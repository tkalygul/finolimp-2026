# Часть 1. Очистка грязного реестра

Вход: 12 146 строк. Выход: 19 023 строки, по одной на билет.

## Шаг 1. Чтение файла без порчи данных

**Что я увидела.** Реестр — CSV, набранный людьми. Номера билетов похожи на числа. Файл мог быть пересохранён в Excel, тогда кодировка Windows-1251.

**Что я решила сделать.** Читать каждую ячейку ровно как написано. 13-значный билет не должен превратиться в `8.45e+12`. Номера строк должны остаться верными, чтобы бухгалтер нашёл строку в исходном файле. Если файла нет или их два — остановиться с понятным сообщением.

**Как это обычно решают аналитики.** Читают с `dtype=str` и отключают автоугадывание пустых значений. Колонки проверяют схемой (pandera, Great Expectations) или простым списком обязательных колонок.

**План шага.** 1) Найти ровно один `registry*.csv`. 2) Читать всё как текст, пустые строки сохранять. 3) Сначала UTF-8, затем cp1251. 4) Проверить колонки.

**Как реализовано.**
```python
options = dict(dtype=str, keep_default_na=False, skip_blank_lines=False)
try:
    return pd.read_csv(path, encoding="utf-8-sig", **options)
except UnicodeDecodeError:
    return pd.read_csv(path, encoding="cp1251", **options)
```
`skip_blank_lines=False` сохраняет нумерацию. Поэтому `row_id = f"registry:{i + 2}"` совпадает с номером строки в Excel (строка 1 — заголовок). Нет файла или их несколько — `InputFileError`.

**Файлы.** `find_input_file`, `read_csv_text` в `load_registry.py`. Колонки проверяет `validate()` Калыгул в `src/schema.py`.

## Шаг 2. Один субагент, много написаний → один ключ

**Что я увидела.** Одна компания встречается как `ОсОО Иссык Трип`, `иссык трип`, `ИССЫК ТРИП`, `Иссык Трип ` (пробел в конце), `ОсОО "Иссык Трип"`.

**Что я решила сделать.** Привести всё к одному значению, чтобы реестр правильно склеивался с 1С и ETM.

**Как это обычно решают аналитики.** Нормализуют текст: нижний регистр, убрать знаки, убрать юридические формы, убрать пробелы. Важно, чтобы все команды использовали одну и ту же функцию.

**План шага.** Нижний регистр → `ё` в `е` → убрать кавычки → убрать ОсОО/ООО/ИП/ЗАО/ОАО → убрать все пробелы.

**Как реализовано.**
```python
s = str(name).lower().replace("ё", "е")
s = _QUOTES.sub("", s)          # «» " “ ” ' `
s = _LEGAL_FORM.sub(" ", s)     # осоо|ооо|ип|зао|оао
return re.sub(r"\s+", "", s)    # → "иссыктрип"
```
Пустые ячейки (None, NaN, `pd.NA`) дают `""`, а не текст «nan».

**Файлы.** `subagent_key` в `normalize.py`. Аргумент для жюри: `cleaning.py` (P2) импортирует эту же функцию, это проверяет тест `test_p2_uses_same_subagent_key`.

## Шаг 3. Кто контрагент: субагент, корпоративный клиент или неизвестный

**Что я увидела.** В ETM 100 субагентов. Часть названий в реестре обрезана: `Сатар уулу` вместо `Сатар уулу Санжар`. `Джолдош уулу` подходит двум субагентам. Часть строк — корпоративные клиенты, не субагенты.

**Что я решила сделать.** Привязать каждую строку к правильному субагенту. Корпоративных держать отдельно. Не угадывать, если ответов два.

**Как это обычно решают аналитики.** Сначала join по справочнику. Остаток часто добивают нечётким поиском (rapidfuzz, расстояние Левенштейна). С деньгами это рискованно: неверное совпадение переносит деньги на другую компанию.

**План шага.** Проверки по порядку:
1. Точный ключ есть в ETM → субагент (`exact`).
2. Ключ есть в списке корпоративных → корпоративный.
3. Ключ — начало ровно одного имени в ETM (только если ключ от 6 символов) → `prefix`.
4. Начало нескольких имён → смотрим, кому ETM продал этот билет. Если ровно одному → `prefix_ticket`.
5. Иначе → проблемная строка (`party_unknown` / `party_ambiguous`).

**Как реализовано.**
```python
candidates = sorted(k for k in etm_keys if k.startswith(key)) if len(key) >= MIN_PREFIX_LEN else []
if len(candidates) > 1:
    by_ticket = set()
    for t in tickets:
        by_ticket |= ticket_agents.get(t, set()) & set(candidates)
    if len(by_ticket) == 1:
        return "subagent", by_ticket.pop(), "prefix_ticket", None
    return "unresolved", None, "none", "party_ambiguous"
```
На выданных данных так решаются 19 обрезанных имён. Отделяются 423 корпоративные строки.

**Файлы.** `resolve_party`, `load_etm_reference`, `load_corporate_keys` в `load_registry.py`. Список корпоративных: `reference/corporate_clients.csv`.

## Шаг 4. Номера билетов в любом формате

**Что я увидела.** Один билет пишут как `604-2461885130`, `6042461885130` или `2461885130`. В одной ячейке бывает несколько билетов через пробел, `,`, `;` или `/`. Так в 4 304 строках.

**Что я решила сделать.** Один формат для всех трёх источников: последние 10 цифр. Всё, что не билет, отвергать, а не молча пропускать.

**Как это обычно решают аналитики.** Делят регулярным выражением, убирают нецифры, оставляют ключ фиксированной длины.

**План шага.** Разбить ячейку → каждый кусок обязан быть `3-10`, 13 или 10 цифр → взять последние 10 → один билет дважды в ячейке нельзя.

**Как реализовано.**
```python
_TICKET = re.compile(r"\d{3}-\d{10}|\d{13}|\d{10}")
bad = [p for p in parts if not _TICKET.fullmatch(p)]
if bad:
    raise ParseError("bad_ticket_format", ", ".join(bad))
result = [p.replace("-", "")[-10:] for p in parts]
```
Ошибки — это `ParseError` с кодом причины. Код потом становится `parse_status` строки.

**Файлы.** `tickets10` в `normalize.py`.

## Шаг 5. Числа в разных форматах записи

**Что я увидела.** `115 877,00`, `16.094,00`, `10 116.00`, `20062`. То точка отделяет тысячи, то дробь.

**Что я решила сделать.** Читать все правильно. Если смысл неясен — сказать об этом, а не гадать.

**Как это обычно решают аналитики.** `pd.to_numeric` после replace или разбор с учётом локали. Оба молча ошибаются на смешанных форматах.

**План шага.** Разделитель правее — десятичный. Группы тысяч ровно по 3 цифры. Одиночное `12.345` может быть двенадцатью тысячами или 12,345, поэтому помечается `ambiguous_number`.

**Как реализовано.**
```python
if has_dot and has_comma:
    dec = "." if s.rfind(".") > s.rfind(",") else ","
...
# Одиночное 12.345 может быть и тысячами, и дробью, поэтому не угадываем
if dec and thou is None and " " not in int_part and len(frac) == 3:
    raise ParseError("ambiguous_number", raw)
```
Обычные, неразрывные (`\xa0`) и узкие (` `) пробелы считаются одинаково.

**Файлы.** `parse_number` в `normalize.py`.

## Шаг 6. Ячейка суммы: валюта, сервисный сбор, штраф

**Что я увидела.** В одной ячейке несколько значений: `115 877,00 kzt + 500 kgs sf`, `usd 326 + 1000KGS sf`, `-20 371,11 kgs (штраф 25%)`. Валюта то до числа, то после. В 65 строках вместо суммы стоит номер билета.

**Что я решила сделать.** Достать четыре вещи: основная сумма и её валюта, сбор и его валюта, процент штрафа.

**Как это обычно решают аналитики.** Регулярные выражения с именованными группами (`str.extract`).

**План шага.** 1) Вырезать `(штраф N%)`. 2) Разделить по `+` на основную часть и сбор. 3) Распознать `ВАЛЮТА число` или `число ВАЛЮТА`. 4) Сбор обязан заканчиваться на `sf`. 5) На каждый вид сбоя — точный код ошибки.

**Как реализовано.**
```python
m = _MAIN.fullmatch(main)
if not m:
    if _BARE_TICKET.fullmatch(main):
        raise ParseError("ticket_in_amount", raw)   # те самые 65 строк
    if re.fullmatch(_NUM, main):
        raise ParseError("no_currency", raw)
    raise ParseError("bad_amount_format", raw)
```
Результат — небольшой объект `Pay(amount, currency, fee, fee_currency, penalty_pct)`. Допустимы 5 валют: KGS, USD, EUR, RUB, KZT.

**Файлы.** `parse_pay`, `Pay` в `normalize.py`.

## Шаг 7. Перевод в сомы со знаком, как в ETM

**Что я увидела.** Суммы в 5 валютах. Курс лежит в той же строке (`rate_usd` … `rate_kzt`). Операции: 11 006 продаж, 672 возврата, 468 войдов.

**Что я решила сделать.** Перевести всё в сомы. Взять знак как в ETM, чтобы суммы сравнивались напрямую: продажа уменьшает депозит, возврат и войд увеличивают.

**Как это обычно решают аналитики.** Присоединяют таблицу курсов по дате и умножают. Здесь курс уже в каждой строке, его и берём.

**План шага.** Сумма × курс строки + сбор × курс сбора. Продажи делаем отрицательными. Затем проверяем смысл: знак должен подходить операции, у возврата нет сбора, у продажи нет штрафа.

**Как реализовано.**
```python
gross = abs(pay.amount) * fx + (pay.fee or 0.0) * (fee_fx or 0.0)
amount_row_kgs = -gross if op == "sale" else gross
if op == "sale" and pay.amount <= 0 or op in ("refund", "void") and pay.amount >= 0:
    problem(ParseError("sign_mismatch", ...))
```
Нет курса или он нулевой — `bad_rate`, а не неверная сумма.

**Файлы.** `_rate`, `parse_row` в `load_registry.py`.

## Шаг 8. Проблемные строки помечаем, не удаляем. Дубли тоже

**Что я увидела.** У некоторых строк сразу несколько проблем. Некоторые строки — точные копии других: 60 лишних копий.

**Что я решила сделать.** Оставить все строки и сказать, что с каждой не так. Дубль может быть настоящей ошибкой (деньги списаны дважды), поэтому бухгалтер должен его видеть.

**Как это обычно решают аналитики.** Складывают плохие строки в отдельную таблицу-карантин. Часто делают `drop_duplicates()`, но это прячет ошибки двойного ввода.

**План шага.** Копить все причины по строке, а не останавливаться на первой. Проблемные строки писать в отдельный файл с кодами и подробностями. У дублей запоминать оригинал и помечать лишние копии.

**Как реализовано.**
```python
status = "ok" if not p["reasons"] else ";".join(p["reasons"])   # например "bad_date;no_currency"
...
dup_mask = raw.duplicated(keep=False)
first = first_of_group.setdefault(values, rid)

```

**Файлы.** `parse_row`, `load_registry` → `registry_rejects.csv`, колонки `dup_group` и `is_dup_extra`.

## Шаг 9. Одна строка на билет

**Что я увидела.** Одна строка реестра может покрывать 4 билета с одной общей суммой. 1С и ETM работают по билетам.

**Что я решила сделать.** Сделать по строке на билет. Делить сумму так же, как бот ETM: поровну.

**Как это обычно решают аналитики.** `df.explode("tickets")`, затем делят сумму на число билетов.

**План шага.** На каждый билет строка с его номером, позицией в строке и суммой ÷ число билетов. Заодно привести к порядку пассажиров, PNR, авиакомпанию, маршрут. Пометить строки, где пассажиров не столько, сколько билетов.

**Как реализовано.**
```python
for seq, ticket in enumerate(p["tickets"], start=1):
    out_rows.append({ ..., "ticket10": ticket, "ticket_seq": seq,
        # Сумму строки делим поровну между билетами, как это делает бот

**Как это обычно решают аналитики.** pandas `to_excel`, затем openpyxl или xlsxwriter для оформления.

**Как реализовано.**

if marked: cell.fill = WARN_FILL

```

## Вероятные вопросы жюри

- **Почему не нечёткий поиск имён?** Неверное совпадение переносит деньги на другого субагента. Принимаются только точное совпадение, совпадение по началу имени или подтверждение по билету.
- **Почему не удалять дубли?** Дубль может быть настоящим двойным списанием. Он помечается, решает бухгалтер.
- **Почему не угадывать `12.345`?** Возможны оба смысла. Ошибка при неверном выборе — в 1 000 раз. Строка идёт в список проблемных.
- **Как вы знаете, что ничего не потеряно?** Без проблем + проблемные = 12 146. Билетных строк ровно столько, сколько билетов. Каждая продажа бота в ETM найдена в реестре.
